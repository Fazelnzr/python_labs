## 2. Постановка задачі (Варіант 7)

Розробити надійний модуль імпорту, валідації, фільтрації, конфігурації та експорту системи оцінювання студентів.
- **Поля вхідних даних:** `student_id`, `name`, `discipline`, `grade`.
- **Правила валідації:**
  - `student_id` — ціле додатне число (`> 0`);
  - `name` — непорожній рядок ПІБ студента (коректні літери, пробіли, дефіс, апостроф);
  - `discipline` — непорожня назва навчальної дисципліни, що входить до дозволеного переліку `allowed_disciplines` із `config.yaml`;
  - `grade` — числове значення оцінки в діапазоні `0 <= grade <= 100`.
- **Функціональні вимоги:**
  - Потоковий імпорт (streaming import) без завантаження всього файлу в оперативну пам'ять;
  - Підтримка режимів `strict` (`skip_invalid: false`) та `tolerant` (`skip_invalid: true`);
  - Зовнішня YAML-конфігурація з переліком дозволених дисциплін (`allowed_disciplines`) та порогом успішності (`passing_grade`);
  - Фільтрація записів за порогом успішності та атомарний потоковий експорт у `JSON`;
  - Підрахунок статистики (`total`, `valid`, `invalid`, `passed`, `failed_threshold`, `exported`);
  - Ведення основного журналу `logs/application.log`, окремого журналу помилок `logs/errors.log`, окремого CSV-звіту некоректних записів `output/invalid_records.csv` та підсумкового звіту `output/summary_report.json`.

## 4. Ієрархія власних винятків (`exceptions.py`) та Exception Chaining

```text
Exception
 └── ApplicationError
      ├── ConfigurationError
      └── DataError
           ├── DataImportError
           ├── DataValidationError
           │    └── RecordValidationError (line_number, field, raw_value)
           └── DataExportError
```

- `ApplicationError` — кореневий виняток застосунку, який перехоплюється на верхньому рівні `main.py` для контрольованого завершення з кодом `1`.
- `ConfigurationError` — сигналізує про помилки файлу `config.yaml` або порушення інваріантів конфігурації (fail-fast).
- `DataImportError` — помилки відкриття вхідного файлу або порушення структури формату (CSV/JSON/YAML).
- `RecordValidationError` — містить атрибути `line_number`, `field`, `raw_value` для точного діагностування рядка та поля, де виникла помилка.
- `DataExportError` — помилки серіалізації або запису вихідного файлу.

**Приклад Exception Chaining (`validators.py`):**

```python
try:
    grade = float(str(raw_grade).strip())
except (KeyError, TypeError, ValueError) as error:
    raise RecordValidationError(
        "Grade must be a numeric value",
        line_number=line_number,
        field="grade",
        raw_value=raw_grade,
    ) from error
```

Конструкція `raise ... from error` зберігає першопричину (`__cause__ = ValueError`) всередині доменного винятку `RecordValidationError`.

## 7. Результати експериментів

### Експеримент 1. Strict vs Tolerant mode (1000 valid + 10 invalid records)

| Параметр | Strict (`skip_invalid: false`) | Tolerant (`skip_invalid: true`) |
|---|---|---|
| Оброблено записів (`total`) | `100` (зупинка на першому помилковому рядку 101) | `1010` |
| Valid | `99` | `1000` |
| Invalid | `1` | `10` |
| Exported | `0` (тимчасовий `.tmp` видалено) | `1000` |
| Завершення application | Контрольована зупинка (`RecordValidationError` → `SystemExit(1)`) | Успішне завершення (`0`) |

**Висновок:** **Strict mode** доцільний для фінансових транзакцій, міграцій критичних реєстрів або синхронізації баз даних, де неприпустима втрата жодного рядка (принцип «усе або нічого»). **Tolerant mode** доцільний при імпорті великих відомостей, логів або зовнішніх CSV-вивантажень, де поодинокі помилки введення потрібно залогувати у звіт для виправлення, але не блокувати обробку основної маси коректних даних.

---

### Експеримент 2. Streaming vs Eager (вимірювання часу та пікової пам'яті `tracemalloc`)

| Records | Eager time (s) | Streaming time (s) | Eager peak RAM | Streaming peak RAM | Економія RAM |
|---|---|---|---|---|---|
| `10 000` | `0.1146 s` | `0.1197 s` | `4 823.95 KB` (`4.71 MB`) | `72.68 KB` (`0.07 MB`) | **у 66.4 раза** |
| `100 000` | `1.2017 s` | `1.0449 s` | `47 974.12 KB` (`46.85 MB`) | `72.62 KB` (`0.07 MB`) | **у 660.6 раза** |
| `500 000` | `5.3313 s` | `5.1461 s` | `240 324.05 KB` (`234.69 MB`) | `72.58 KB` (`0.07 MB`) | **у 3311.3 раза** |

**Висновок:** При жадібному завантаженні (`list(csv.DictReader(file))`) споживання оперативної пам'яті зростає лінійно `O(N)` і на `500 000` записах перевищує `234 МБ`. При потоковій обробці через генератор (`yield from`) пікове споживання пам'яті залишається сталим `O(1)` — близько `72.6 КБ` незалежно від розміру файлу, при цьому час виконання залишається співмірним (навіть трохи меншим на великих обсягах завдяки відсутності витрат на алокацію гігантського списку та збирання сміття).

### Експеримент 4. Atomic Output

Під час імітації аварійного збою (`OSError: Simulated disk write failure mid-stream`) посеред експорту в файл, де вже зберігався попередній валідний результат:
- Перехоплено виняток: `DataExportError: Cannot export JSON data to .../grades.json (cause: OSError)`;

- Тимчасовий файл `grades.json.tmp` **гарантовано видалено** (`tmp_file_exists = False`).

## 8. Відповіді на контрольні запитання

1. **Що таке exception?** — Це спеціальний об'єкт у Python, який сигналізує про виняткову або помилкову ситуацію під час виконання програми та перериває звичайний потік виконання до моменту перехоплення.
2. **Для чого використовується `try`?** — Блок `try` охоплює код, у якому потенційно може виникнути виняток.
3. **Для чого `except`?** — Блок `except` перехоплює й обробляє вказані типи винятків, що виникли у блоці `try`.
4. **Коли виконується `else` після `try`?** — Тільки тоді, коли в блоці `try` не виникло жодного винятку.
5. **Коли виконується `finally`?** — Завжди при виході з конструкції `try` (незалежно від того, чи був виняток, чи виконався `return`/`break`).
6. **Для чого використовується `raise`?** — Для явного генерування (підняття) нового винятку або повторного підняття поточного.
7. **Що означає `raise` без аргументів?** — Повторно передає вже перехоплений в `except` поточний виняток вище по стеку зі збереженням оригінального стек-трейсу.
8. **Чому не рекомендується `except: pass`?** — Він приховує як очікувані помилки даних, так і програмні помилки (`NameError`, `TypeError`) і системні сигнали (`KeyboardInterrupt`, `SystemExit`), що робить діагностику неможливою.
9. **Чому потрібно перехоплювати конкретні exception types?** — Щоб обробляти лише ті помилки, які очікуються в цьому місці і для яких відома коректна стратегія відновлення, не маскуючи баги в коді.
10. **Що таке exception hierarchy?** — Це деревоподібна структура класів винятків, пов'язаних наслідуванням від базового класу (наприклад, `ApplicationError -> DataError -> RecordValidationError`).
11. **Для чого створювати custom exceptions?** — Щоб відокремити помилки предметної області від низькорівневих системних винятків, передавати додатковий контекст (`line_number`, `field`) і гнучко керувати перехопленням на різних рівнях архітектури.
12. **Що таке exception chaining?** — Це механізм пов'язування нового винятку з попереднім винятком, який став його безпосередньою причиною (`__cause__`).
13. **Що означає `raise ... from ...`?** — Явно встановлює оригінальний виняток в атрибут `__cause__` нового винятку.
14. **Яку перевагу дає chaining для debugging?** — У traceback відображається і бізнес-контекст помилки, і точна низькорівнева технічна першопричина.
15. **Що означає EAFP?** — *Easier to Ask Forgiveness than Permission*: спробувати виконати операцію в `try` і обробити виняток в `except`, замість численних попередніх перевірок.
16. **Що означає LBYL?** — *Look Before You Leap*: перевірити всі умови (`if ...`) перед виконанням операції.
17. **Що таке fail-fast?** — Принцип проєктування, за яким система негайно повідомляє про помилку щойно виявляє некоректний стан або конфігурацію, не розпочинаючи тривалу обробку.
18. **Де доцільно застосовувати fail-fast?** — Під час старту програми: при завантаженні конфігурації, перевірці наявності вхідних файлів, змінних середовища та прав доступу.
19. **Що таке context manager?** — Об'єкт, який керує життєвим циклом ресурсу: виділяє ресурс на вході в блок `with` і гарантовано звільняє його на виході.
20. **Для чого використовується `with`?** — Для безпечної роботи з ресурсами (файлами, з'єднаннями, транзакціями) з гарантованим виконанням завершальних дій навіть у разі винятку.
21. **Які methods утворюють context manager protocol?** — Методи `__enter__(self)` та `__exit__(self, exc_type, exc_value, traceback)`.
22. **Що робить `__enter__()`?** — Ініціалізує ресурс і повертає об'єкт, який зв'язується зі змінною після `as`.
23. **Що робить `__exit__()`?** — Звільняє ресурс після завершення блоку `with`; якщо повертає `False`, виняток (якщо він стався) поширюється далі.
24. **Чи закриває `with` файл при exception?** — Так, метод `__exit__()` викликається гарантовано навіть при виникненні будь-якого винятку всередині блоку.
25. **Для чого `contextlib.contextmanager`?** — Декоратор, що дозволяє створювати контекстні менеджери на основі функції-генератора без написання окремого класу з `__enter__`/`__exit__`.
26. **Яку роль має `yield` у generator-based context manager?** — Розділяє код ініціалізації (`__enter__`, до `yield`) і код очищення (`__exit__`, у блоці `finally` після `yield`), а також передає значення у змінну `as`.
27. **Що таке `pathlib.Path`?** — Об'єктно-орієнтований клас стандартної бібліотеки Python для кросплатформної роботи з файловими шляхами.
28. **Чому `pathlib` кращий за ручну конкатенацію шляхів?** — Автоматично враховує роздільники ОС (`/` або `\`), надає зручні методи перевірки й маніпуляції шляхами (`.exists()`, `.with_suffix()`, `.parent`, `.mkdir()`).
29. **Для чого задається `encoding="utf-8"`?** — Щоб гарантувати однакове та коректне читання/запис символів (зокрема кирилиці) незалежно від системної локалі ОС (наприклад, `cp1251` на Windows).
30. **Що таке CSV?** — *Comma-Separated Values* — табличний текстовий формат, де записи розділені переносами рядків, а поля — комами (або іншим роздільником).
31. **Для чого `csv.reader`?** — Построково читає CSV-файл, повертаючи кожний рядок як список рядків `list[str]`.
32. **Для чого `csv.DictReader`?** — Читає CSV-файл і повертає кожний рядок як словник `dict[str, str]`, де ключами є назви стовпців із першого рядка заголовка.
33. **Чим `DictReader` зручний для structured data?** — Звернення до полів відбувається за осмисленими іменами (`row["grade"]`), а не індексами (`row[3]`), що робить код стійким до зміни порядку стовпців.
34. **Для чого `csv.DictWriter`?** — Для запису словників у CSV-файл відповідно до заданого списку стовпців `fieldnames`.
35. **Що таке JSON?** — *JavaScript Object Notation* — стандартний текстовий формат обміну структурованими даними (об'єкти, масиви, рядки, числа, булеві значення, `null`).
36. **Що таке serialization?** — Процес перетворення об'єктів у пам'яті програми на послідовність байтів або текстовий формат (JSON, YAML, CSV) для збереження чи передачі.
37. **Що таке deserialization?** — Зворотний процес відновлення структур даних та доменних об'єктів програми із зовнішнього серіалізованого формату.
38. **Чим `json.dump()` відрізняється від `json.dumps()`?** — `json.dump()` записує JSON безпосередньо у файловий потік (`file-like object`), а `json.dumps()` повертає серіалізований JSON як рядок `str`.
39. **Чим `json.load()` відрізняється від `json.loads()`?** — `json.load()` читає JSON із файлового об'єкта, а `json.loads()` парсить JSON із рядка `str`.
40. **Що таке `JSONDecodeError`?** — Виняток модуля `json`, що виникає, коли вхідний текст не є синтаксично коректним JSON-документом.
41. **Для чого використовується YAML?** — Для зручного людиночитаного опису конфігураційних файлів із підтримкою ієрархічної структури та коментарів.
42. **Чому рекомендується `yaml.safe_load()`?** — Бо звичайний `yaml.load()` може виконувати довільні Python-об'єкти з YAML-файлу, що створює критичну вразливість безпеки (Remote Code Execution).
43. **Які типові сценарії використання JSON?** — REST API, міжсервісний обмін даними, структурований експорт результатів, кешування.
44. **Які типові сценарії використання YAML?** — Конфігураційні файли застосунків (`config.yaml`), CI/CD пайплайни, Docker Compose, Kubernetes маніфести.
45. **Що таке configuration file?** — Зовнішній файл із параметрами роботи програми (шляхи, пороги, режими, рівні логування), відокремлений від вихідного коду.
46. **Чому configuration краще не hard-code у Python?** — Зовнішня конфігурація дозволяє змінювати поведінку програми для різних середовищ і сценаріїв без редагування коду та повторного деплою.
47. **Що потрібно перевіряти у configuration?** — Наявність обов'язкових секцій і ключів, типи значень, допустимі діапазони (`0 <= passing_grade <= 100`), непорожні списки та існування вхідних файлів.
48. **Що таке logging?** — Систематичний запис подій роботи програми з часовими мітками, рівнями важливості та контекстом у файли або потоки виводу.
49. **Чим `logging` відрізняється від `print()`?** — Підтримує рівні важливості (`DEBUG`..`CRITICAL`), форматування, одночасний запис у кілька приймачів (`FileHandler`, `StreamHandler`), ротацію файлів та автоматичний запис стек-трейсів.
50. **Які існують logging levels?** — `DEBUG` (10), `INFO` (20), `WARNING` (30), `ERROR` (40), `CRITICAL` (50).
51. **Для чого `logger.info()`?** — Для фіксації штатних інформаційних подій (старт/завершення операції, підсумкова статистика).
52. **Для чого `logger.warning()`?** — Для некритичних відхилень (наприклад, пропущений некоректний запис у tolerant mode), після яких програма продовжує роботу.
53. **Для чого `logger.error()`?** — Для серйозних помилок, через які операція або програма не може виконати завдання.
54. **Для чого `logger.exception()`?** — Викликається всередині блоку `except` і записує повідомлення рівня `ERROR` разом із повним traceback поточного винятку.
55. **Що містить traceback?** — Послідовність викликів функцій (файл, номер рядка, назва функції, рядок коду) від місця виникнення винятку до точки його перехоплення, а також ланцюжок пов'язаних винятків.
56. **Чому secrets не можна записувати в logs?** — Лог-файли часто зберігаються у відкритому вигляді та доступні багатьом людям/системам моніторингу, тому потрапляння паролів, токенів чи конфіденційних даних призводить до витоку інформації.
57. **Що таке streaming I/O?** — Потокова обробка даних, за якої записи читаються, валідуються і записуються по одному через ітератори/генератори без завантаження всього набору в RAM.
58. **Яка перевага streaming для великих files?** — Постійне мінімальне споживання оперативної пам'яті `O(1)`, що дозволяє обробляти файли розміром у багато гігабайтів.
59. **Що таке eager file loading?** — Підхід, за якого весь вміст файлу одразу зчитується та матеріалізується в оперативній пам'яті (наприклад, `list(reader)` або `file.read()`).
60. **Чому `list(reader)` може бути небажаним?** — На великих файлах це викликає різке зростання споживання RAM (сотні мегабайтів або гігабайти) і може призвести до `MemoryError`.
61. **Що таке strict validation mode?** — Політика обробки, за якої перший же невалідний запис негайно зупиняє процес імпорту з підняттям винятку.
62. **Що таке tolerant mode?** — Політика обробки, за якої невалідні записи реєструються у логах і лічильнику помилок, пропускаються, а обробка наступних записів триває.
63. **Коли доцільно використовувати strict mode?** — Коли цілісність набору даних є критичною і частковий імпорт є неприпустимим (фінансові реєстри, транзакційні пакети).
64. **Коли tolerant mode?** — Коли вхідні дані надходять із зовнішніх джерел з можливими людськими помилками, і важливо імпортувати всі валідні записи, сформувавши звіт про відхилені рядки.
65. **Що таке atomic write?** — Спосіб запису файлу, за якого цільовий файл або оновлюється повністю і неподільно, або залишається у попередньому валідному стані без частково записаних даних.
66. **Для чого використовується temporary file?** — Щоб виконати весь потенційно тривалий або ризикований запис у `.tmp`-файл і лише після його успішного закриття миттєво замінити основний файл через `replace()`.
67. **Що може статися при звичайному output write та аварійному завершенні?** — Вихідний файл буде обрізаним (пошкодженим, невалідним JSON/CSV), а попередні коректні дані в ньому будуть безповоротно втрачені.
68. **Навіщо видаляти temporary file після error?** — Щоб не засмічувати файлову систему недописаними залишками `.tmp`-файлів після невдалих запусків.
69. **Що таке JSON Lines?** — Текстовий формат (`.jsonl`), у якому кожний окремий рядок є самостійним валідним JSON-об'єктом.
70. **Чому JSON Lines зручний для streaming?** — На відміну від єдиного JSON-масиву `[...]`, формат `.jsonl` дозволяє читати й дописувати записи строго построково без необхідності парсити весь документ.

## 9. Висновок

У ході виконання лабораторної роботи №5 було розроблено надійний модуль імпорту, валідації, конфігурації та експорту системи оцінювання студентів (Варіант 7). Застосовано власну ієрархію доменних винятків із `exception chaining`, fail-fast перевірку YAML-конфігурації, потокову обробку даних через генератори (`Importer` / `Exporter` protocols для CSV, JSON, JSON Lines, YAML), журналювання з ротацією та окремим журналом помилок, а також власні контекстні менеджери (`logged_operation` та транзакційний `AtomicFileWriter`). Експериментально підтверджено, що потокова обробка `500 000` записів зменшує пікове споживання RAM з `234.69 МБ` до `72.58 КБ` (у понад `3300` разів), а атомарний експорт гарантовано захищає вихідні файли від пошкодження у разі аварійного переривання.
